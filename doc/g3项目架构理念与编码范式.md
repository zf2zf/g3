## 1. 架构理念总览

翻遍整个仓库后，可以归纳出七条贯穿性的设计信条：

1. **组件化 + 显式依赖拓扑**。一切服务端组件（server / escaper / backend / collector…）
   都是注册表里的命名对象，彼此**按名字（`NodeName`）引用**，依赖关系显式声明
   （`depends_on` / `dependent_server()`），由 `TopoMap`（`lib/g3-daemon/src/config/topology.rs`）
   做拓扑排序，加载与热重载按依赖方向级联。
2. **解析与实例化严格分离**。`config/` 只把 YAML 变成 `*Config` 结构体存进 parse-time
   registry；运行时对象由 `<plane>/ops.rs` 构造。因此 `--test-config` 能只验配置不启动，
   `--output-*-graph` 能只画依赖图。
3. **热重载 / 热升级是一等公民，不是补丁**。每种配置都实现 `diff_action()` 返回
   `NoAction / Reload / SpawnNew / UpdateInPlace(flags)`；热升级用 SO_REUSEPORT 让新旧进程
   同端口共存，控制面协调排空——不传 fd，逻辑简单且可回退（失败即 `cancel_old_shutdown()`）。
4. **数据面与管控面物理分离**。数据路径（worker 线程池）上绝不做 DNS 定时器、限速 replenish、
   指标聚合、日志格式化这类"后台活"；它们各自有专属的单线程 runtime 或 OS 线程（见第 2 节）。
5. **热路径无锁**。读多写少的配置/路由表用 `ArcSwap`（全仓 68 个文件），全局一次写用
   `OnceLock`，只有低频的管理操作才用 `Mutex<HashMap>` 注册表。
6. **一致性压倒 cleverness**。8 个应用的 `main.rs` 是几乎逐字节相同的固定管线；
   目录一律 `mod.rs / ops.rs / registry.rs / handle.rs / task.rs`。换任何一个应用，
   你找代码的动作完全一样——这是本项目最重要的"可导航性"资产。
7. **宁丢数据不阻塞，宁 panic 不僵死**。日志通道满了 `try_send` 失败就计数丢弃
   （`LogStats{io,drop}`）；任何线程 panic 直接触发全局强制退出（panic hook →
   `trigger_force_shutdown()`），全仓**没有一处 `catch_unwind`**——代理进程带病运行
   比重启危害更大。

## 2. 运行时模型：blended + unaided 的平面分离

Tokio 运行时不是"一个多线程 runtime 走天下"，而是按职责拆成三类（`lib/g3-runtime/`）：

| 概念 | 类型 | 用途 |
|------|------|------|
| **Blended runtime** | `blended/mod.rs` `BlendedRuntimeConfig` | 主运行时：管控、监听 accept、后台任务；`thread_number==0` 时退化为 current-thread |
| **Unaided runtime** | `unaided/mod.rs` `WorkersGuard::VariantC / VariantM` | 数据面 worker 池：VariantC = N 个 OS 线程各跑一个 `new_current_thread` runtime（线程名 `worker#i`）；VariantM = K 个多线程 runtime |
| **专用小 runtime** | `std::thread` + `new_current_thread` | `capnp_ctl`（控制面 RPC）、`limit-schedule`（限速 token 补充）、`stat-main`（指标聚合）、cert-generate、ip-locate |

要点（均可在代码中验证）：

- **每 worker 绑核**：只有 worker 拿 `CpuAffinity`（环境变量 `WORKER_<i>_CPU_LIST`，
  `auto_set_sched_affinity`），`CPU_CORE_WORKER_MAP: OnceLock<FxHashMap>` 支持按核选 worker——
  目的是让 epoll 实例和缓存尽量 NUMA-local。
- **任务分发**：`g3_daemon::runtime::worker::select_handle()` 线程本地轮询（随机起点），
  listen 侧另有原子 CAS 轮询的 `select_listen_handle()`。
- **优雅退出参数集中**：`runtime/config.rs` 的 `server_offline_delay / task_wait_timeout /
  task_quit_timeout / task_wait_delay`，全部可 YAML 配置。
- g3keymess 演示了极简档：`set_default_thread_number(0)`，全进程 current-thread。

```
 ┌─────────────────────────── 一个 g3 守护进程 ───────────────────────────┐
 │  main#i (blended)        控制面：capnp_ctl 线程 / 信号 / 热升级 / QuitActor │
 │  worker#0..N (unaided)   数据面：每连接任务，绑核，绝不跑定时器            │
 │  limit-schedule          限速 token 补充定时任务（独立 current-thread）      │
 │  stat-main               StatsD 聚合线程（delta snapshot → emit）          │
 │  cert-generate / ip-locate  证书代签 / IP 归属查询辅助 runtime             │
 └────────────────────────────────────────────────────────────────────────┘
```

## 3. 三层分层：apps / g3-daemon / lib

```
g3proxy · g3tiles · g3keymess · g3statsd · g3fcgen · g3iploc · g3bench · g3mkcert
        │  业务语义：协议组合、配置模型、审计/认证策略
        ▼
lib/g3-daemon            ← 守护进程"操作系统"层
  opts / config / listen / log(process+event) / runtime(worker) /
  stat / metrics / control(quit+upgrade+local+capnp+text) / register / daemonize
        │  机制不含政策：框架不知道什么是 escaper/backend，只提供
        │  ListenTcpRuntime<S>、BaseServer/ReloadServer、UpgradeAction/QuitAction trait
        ▼
lib/g3-*  ×44            ← 纯协议与工具 crate（g3-http、g3-socks、g3-dpi、
   g3-resolver、g3-io-ext、g3-tls-cert、g3-yaml、g3-types …），不含守护进程逻辑
```

**每个应用的 `main.rs` 都是同一条固定管线**（对比 `g3tiles/src/main.rs` 与
`g3keymess/src/main.rs`，语句级相同）：

```
parse_clap → log::process::setup → UpgradeActor::connect_to_old_daemon
→ config::load → (--test-config 短路) → daemonize::check_enter
→ stat::spawn_working_threads → runtime::worker::spawn_workers → tokio_run {
    capnp::spawn_working_thread → UniqueController::start
    → release_old_controller → DaemonController::start → QuitActor::tokio_spawn_run
    → signal::register → panic::set_hook → <app>::load_and_spawn()
    → control::upgrade::finish }
```

分工判据也很清晰：一段代码若**换个应用还用得上**就下沉到 `lib/`；
若属于"守护进程的通用机制"（监听、重载协调、控制面、指标搬运）就进 `g3-daemon`；
只有带着该协议产品语义的部分才留在应用里。应用与控制面 CLI 的镜像结构
（`<app>/proto/` + `<app>/utils/ctl/` ↔ `lib/g3-ctl`）同理。

## 4. 配置架构：解析与实例化分离

每个"平面"（plane）都是两层目录，一字不差地重复：

```
config/<plane>/{mod.rs, <type>.rs, registry.rs}   ← parse-time：YAML → Any*Config
<plane>/{mod.rs, ops.rs, registry.rs, handle.rs, task.rs}  ← runtime：Config → Arc<T>
```

已验证同构的有：`g3tiles/src/{backend,serve,discover}`、`g3keymess/src/{store,serve}`、
`g3statsd/src/{collect,export,import}`、`g3proxy/src/{serve,resolve,escape,audit,auth}`
（全仓 13 个 `ops.rs`、27 个 `registry.rs`）。

关键机制：

- **g3-yaml 工具箱**：`foreach_kv` 自动为每个 key 附加
  `.context("failed to parse value of key {key}")`；`key::normalize` 让
  `keyless_tcp` 与 `keylesstcp` 等价；`humanize::as_duration` 支持 `10s` 风格；
  `value/*` 下按 feature 提供 speed_limit / rate_limit / regex / histogram 等类型解码器。
- **feature 贯穿配置层**：`g3-yaml` 的 `dpi`、`geoip`、`acl-rule`、`http`、`route` 等
  feature 开关一路传到配置枚举变体上——关掉 `quic`，所有 `#[cfg(feature="quic")]` 的
  配置变体连带消失，配置面与编译面严格对齐（CI 有专门的 feature-matrix clippy job）。
- **`#[derive(AnyConfig)]`**（`lib/g3-macros/src/any_config.rs`）：作用于枚举，按
  `#[def_fn(name, &NodeName)]` 生成保留各变体 `#[cfg]` 的门面分发方法。这是"类型擦除
  的 match 分发"的宏化，替代了手写巨型 match。
- **依赖拓扑**：`TopoMap`/`TopoNode`（Rc/Weak）由各组件的 `dependent_server()`、
  `dependent_resolver()`、`dependent_collector()` 喂边，重载时按序级联。
- **ops 加锁、diff 决策**：每平面一把 `static *_OPS_LOCK: Mutex<()>`，
  ops 内部走 `*_unlocked` 助手；配置变更后由 `diff_action()` 决定四选一的重载语义。
- **可解释性**：`graphviz/mermaid/plantuml` 三个导出器遍历 registry 打印依赖图，
  把"复杂 YAML 到底连成了什么"变成一条命令行。

## 5. 设计模式清单

以下模式全部在多处代码中验证，按"意图"归类：

### 对象管理与注册

| 模式 | 实例 |
|------|------|
| **Registry 单例** | parse-time：`static INITIAL_BACKEND_CONFIG_REGISTRY: Mutex<HashMap<NodeName, Arc<AnyBackendConfig>, FixedState>>`（foldhash 定种，`g3tiles/src/config/backend/registry.rs` 与 `g3keymess/src/config/server/registry.rs` 文本几乎相同）；runtime：`struct BackendRegistry{inner: HashMap<NodeName, ArcBackendInternal, FixedState>}` + 自由函数委托 |
| **Write-once 全局** | `OnceLock`：`MAIN_HANDLE`、`PROCESS_LOGGER`、`DAEMON_GROUP`、`PRE_REGISTER_CONFIG`；main 之前的可变全局用 `g3_types::sync::GlobalInit<T>`（UnsafeCell 封装，`with_mut()/as_ref()`） |
| **热替换读路径** | `ArcSwap`：`g3tiles/src/serve/*/host.rs` 的 `Arc<ArcSwap<AlpnMatch<ArcBackend>>>`、`next_server: ArcSwap<ArcServer>`、`extra_metrics_tags: Arc<ArcSwapOption<MetricTagMap>>`；轮询计数用 `AtomicUsize` CAS，每 worker 计数用 `thread_local!` |
| **公开/内部 trait 分离** | 内部方法以 `_` 前缀区分：`trait BackendInternal: Backend { fn _clone_config(); fn _reload(); fn _update_config_in_place(); }`（`g3tiles/src/backend/mod.rs:51`）——对外接口干净，重载钩子不外泄 |

### 生命周期与协调

| 模式 | 实例 |
|------|------|
| **模板方法（固定管线）** | 第 3 节的 `main.rs` 管线；g3-daemon 提供各步骤实现，应用只填 `load_and_spawn()` |
| **Actor / Controller 家族** | `<app>/src/control/{quit.rs, upgrade.rs, local/, bridge/, capnp/}`：`QuitActor`（协调退出）、`UpgradeActor`（新进程连旧进程）、`UniqueController`（同配置单实例哨兵，await 即存活）、`DaemonController`（接管后服务控制命令） |
| **两阶段启动** | 注册协调：`serve::create_all_stopped()` → 中心注册 → `start_all_stopped()`，失败即 `trigger_force_shutdown()`（`lib/g3-daemon/src/register/` + `g3keymess/src/register.rs`） |
| **协议嗅探复用** | 控制面 unix socket 上 Text 命令可"升级"为 Cap'n Proto RPC：`CtlProtoCtx<R,W>` 嗅探 `CtlProtoType::{Text, CtlProtoType::CapnP, End}`（`lib/g3-daemon/src/control/mod.rs`）——一个监听口兼容人肉 `nc` 与程序客户端 |

### 组合与分发

| 模式 | 实例 |
|------|------|
| **Combinator / 装饰器** | `route_*` 类 escaper 持有下游 `ArcEscaper` 集合形成出口树（`route_failover`、`route_select`、`route_upstream`…）；g3tiles 的 backend 组合同构 |
| **类型擦除分发** | `Any*Config` 枚举 + `#[derive(AnyConfig)]`（见第 4 节） |
| **Null Object** | 统计钩子的空实现：`g3-io-ext` 的 `Nil*Stats`（`LimitedReader/LimitedWriter/LimitedStream` 的 stats-as-trait-object，不需要观测时零成本挂空） |

### 数据面基础设施

| 模式 | 实例 |
|------|------|
| **统一流抽象** | `g3-io-ext::AsyncStream` 收编 plain/openssl/rustls/QUIC 四种流；`StreamCopy{Config{buffer_size 16KiB, yield_size 1MiB}}` 取代散落的 `tokio::io::copy`（全仓仅 46 处，且几乎都在库内） |
| **准入控制** | `GaugeSemaphore` + `GaugeSemaphorePermit`：并发上限任务把 `_alive_permit` 存在连接上下文里，drop 即释放 |
| **限速与业务分离** | `GlobalLimitGroup::{Server, User, UserSite}` 三组令牌桶/固定窗口（`g3-io-ext/src/limit/`），replenish 定时器跑在独立 `limit-schedule` 线程，worker 只做 O(1) 取币 |
| **Drop 不阻塞的日志** | `AsyncLogger<T,F>` 实现 `slog::Drain`：格式化后 `kanal::bounded(1024)` `try_send`，溢出只往 `LogStats{io,drop}` 记数；sink 库（fluentd/journal/stdlog）各自起 `thread_number` 个 `AsyncIoThread` 带 `retry_queue` 消费 |
| **log→slog 桥接** | `lib/g3-daemon/src/log/process.rs` 按 opts 选 journal/syslog/stdlog 后端，装 `slog::Logger` 并注册 `BridgeLogger: log::Log`——lib 里用 `log::info!`，最终汇入应用选的 slog 管道 |
| **Recorder/Stats/Snapshot 三件套** | 指标统一形态：`*Recorder` 写入、`*Stats` 共享计数、`*Snapshot` 取 delta；stat-main 线程按 `StatId` `wrapping_sub` 出增量，且 `retain(|| Arc::strong_count > 1)` 保证对象销毁前最后一段计数不丢 |
| **FFI 隔离区** | 原始绑定一律关进 `ffi.rs`（`lib/g3-openssl/src/ffi.rs`：`#![allow(unused)]`、opaque newtype `pub enum ASYNC_JOB {}`、按 OpenSSL 版本 `#[cfg(osss300)]` 门控）；外面是 driver trait + Handle/Runtime 适配器把 C 错误翻译成本地错误类型（`g3-resolver/src/driver/c_ares/`）；平台系统调用 shim 分文件 `{unix,windows,macos}.rs`（`g3-io-sys`） |

## 6. 编码范式

### 错误处理分层

- **`anyhow` = 应用/框架边界**（lib 210 文件、g3proxy 212 文件）：配置加载、ops、control、
  main；风格是 `anyhow!("no backend with name {name} found")` + `.context(format!(…))`，
  错误消息携带 inline captured 变量（edition 2024）。
- **`thiserror` = 叶子协议/IO 类型**（lib 70 文件）：`StreamCopyError`、`ResolveError`、
  `UdpCopyClientError` 等——需要被上层 match 的分类错误才有具体类型，否则一律 `anyhow`。
- **panic 政策**：不设防（无 `catch_unwind`），`control/panic.rs` 装 hook：记录
  `thread '<name>' panicked at file:line:col` → `trigger_force_shutdown()`
  （`--monitored` 时改为向父进程发 SIGHUP），`TRIGGER_PANIC_QUIT: AtomicBool` 防重入。
- **被接受的 `unwrap()`**：`Mutex::lock()`、`OnceLock::set`、channel send——"这些失败即
  程序性崩溃"的场景明确允许，其余避免。
- **编译期防御**：feature 组合非法直接 `compile_error!`（如 rustls provider 缺失，
  `g3proxy/src/main.rs:33`、`g3tiles/src/main.rs:33`）。

### 命名与文件组织约定

| 类别 | 约定 | 例 |
|------|------|----|
| 文件 | 每文件一个类型族；固定角色名 `mod.rs / ops.rs / registry.rs / handle.rs / task.rs / server.rs / stats.rs / error.rs / accept.rs / relay.rs / driver.rs` | `g3proxy/src/serve/http_proxy/task/connect/task.rs` |
| 类型 | `Any*Config`（配置枚举）、`Arc<T>` 别名 `ArcThing`、内部 trait `*Internal`、`*DiffAction`、`*Actor`、`*Controller`、泛型运行时 `*Runtime<S>`、指标 `*Recorder/*Stats/*Snapshot` | `ListenTcpRuntime<S>`、`AnyServerConfig` |
| 常量 | 指标名常量 `const METRIC_NAME_*: &str`，命名格式 `<plane>.<obj>.<unit|stage>` | `server.task.alive`、`escaper.tls.handshake.timeout` |
| 头文件 | 每个 `.rs`（约 1819 个）以 `SPDX-License-Identifier: Apache-2.0` + `Copyright <years> ByteDance and/or its affiliates.` 块开头，位于文件最顶端 | — |

### 质量门禁

- **格式化**：默认 rustfmt（无 `.rustfmt.toml`），且 `cargo fmt` **不在 CI**——格式靠
  自觉，硬门槛是 clippy：`cargo clippy --tests -- --deny warnings`，`.clippy.toml` 定制了
  `large-error-threshold=256`、`enum-variant-size-threshold=600`（适配本项目巨型配置枚举）。
- **依赖治理**：`deny.toml`（cargo-deny）。
- **测试布局**：压倒性使用 `#[cfg(test)]` 同文件单元测试（289 个文件）；集成测试目录仅
  `lib/g3-dpi/tests`、`lib/g3-macros/tests`；`yaml_str!/yaml_doc!` 宏主要服务于
  配置解析测试；e2e 辅助在 `scripts/test/*.py`。
- **CI 矩阵**：`.github/workflows/` 的 linux.yml（含逐组件
  `--no-default-features --features <set>` clippy 矩阵）、static.yml（musl +
  vendored-openssl/tongsuo）、cross.yml、macos.yml、windows.yml（MSVC crt-static + vcpkg）、
  codecov.yml、codeql.yml、sphinx.yml。
- **工具链**：edition 2024、`rust-version = 1.90`、`resolver = "3"`；自定义 profile：
  `release-lto`（LTO+strip）、`release-dbg`（保留调试信息）、`release-z`（opt-level=z +
  LTO + panic=abort，体积敏感场景）。

### 协议与代码生成

- 控制面**只用 Cap'n Proto**（全仓无 protobuf/prost）。schema 在 `<app>/proto/schema/*.capnp`，
  `proto/build.rs` 调 `capnpc::CompilerCommand` 生成到 `OUT_DIR`，或以
  `G3_CAPNP_USE_PRECOMPILED` + `G3_CAPNP_GENERATE_DIR` 改用已提交的 `gen/`；
  重新生成：`cargo run -p capnp-generate -- <app>/proto`。
- 构建元信息集中在 `lib/g3-build-env`：每个 `build.rs` 都是
  `check_basic / check_openssl / check_rustls_provider` + `cargo:rustc-env`，应用侧
  `<app>/src/build.rs` 的 `print_version(verbose)` 消费 `G3_OPENSSL_VARIANT`、
  `G3_RUSTLS_PROVIDER` 等——`g3proxy -V` 能直接报出编译时 TLS 变体。
- PR 规范（`CONTRIBUTING.md`）：标题 `area: message`，squash-merge。

## 7. 规范哲学：RFC 为纲

`doc/standards.md` 是全仓库的"规范引用索引"：URI、HTTP/1-3、SOCKS、DNS、TLS/TLCP
（含国密 GB/T 38636-2020）、QUIC、FTP、SMTP/IMAP 全家桶、ICAP、PROXY protocol、
Happy Eyeballs（RFC 8305）、syslog/journal/fluentd/statsd 等数百条 RFC/IETF/IEEE 引用。

它传递的范式是：**实现以标准文本为唯一事实来源，歧义时优先主流实现行为**
（文件开篇原话："The code should comply to these, but should be more compliant to
existing popular implementations"）。对新贡献者的实操含义：

- 写协议解析前，先到 standards.md 找对应 RFC 并读原文；
- 非标准扩展（如 easy-proxy、dynamic-egress-path）要有专文（`doc/easy-proxy.md`）；
- 行为拿不准时对照squid/nginx/Go 等主流实现，而非自创语义。

## 8. 照着范式扩展：三步自检

在任何一个应用中新增/修改功能时，用这三问对齐仓库范式：

1. **放对层了吗？**——协议逻辑进 `lib/g3-*`，守护机制进 `g3-daemon`，业务语义才进应用；
   需要观测的一律走 `*Recorder/*Stats` + statsd 命名格式，需要限并发的一律用 `GaugeSemaphore`。
2. **配对形了吗？**——新组件 = `config/<plane>/<type>.rs`（parse）+ `<plane>/<type>/`
   （runtime）+ registry 注册 + `diff_action()` 重载语义 + `depends_on` 声明 +
   sphinx rst 文档，五件套缺一不可。
3. **守对线了吗？**——热路径不引入 `Mutex<HashMap>` 查找（用 ArcSwap 或建连时解析一次）；
   后台定时任务不起在 worker runtime 上；错误按 anyhow/thiserror 边界分层；
   文件头补 SPDX；提交前 `just qa` 全绿。
